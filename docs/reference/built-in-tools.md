# Built-in tools

The server has tools of its own, which it runs itself when the model calls them. The client sees only the reply they lead to, on every endpoint that chats: chat completions, Responses, Realtime and `/v1/voice`.

- **`get_time`:** the local date, time and time zone. It's on by default.
- **`estimate_distance`:** how far something in the user's latest photo is, with MoGe-2. The model names a part of the photo ("the left") or an object ("the chair"); YOLOX finds the object, and the reply also lists the other objects it saw, so "what's in front of me?" gets an answer too. Things YOLOX doesn't know, such as a tree or a door, CLIPSeg finds by name; what neither finds is measured by where the model says it is. It's on by default.
- **`identify_sounds`:** the sounds in the user's latest recording, with PANNs: "what's that sound?" The model can hear speech itself, but it's poor at other sounds. It's on by default.
- **`identify_speakers`:** who is speaking in the user's latest recording, and when, with pyannote: how many voices, enrolled ones by name, and each turn. It's on by default.
- **`tune_instrument`:** the note in the user's latest recording, with CREPE, and how many cents sharp or flat; for a named instrument, its nearest string and whether to tighten or loosen it. It's on by default.
- **`read_text`:** the text in the user's latest photo, word for word, with PP-OCRv6: "what does this sign say?" The model can see photos itself, but misreads small or dense text. Lines the reader is unsure of are marked, so the model can say so. It's on by default.
- **`describe_people`:** the people in the user's latest photo: how many, each face's expression and whether it's looking at the camera, and raised hands with the fingers they hold up, with YOLOX, YuNet, HSEmotion, L2CS-Net and RTMPose. Expressions are left to the model for faces under 48 pixels tall, which HSEmotion misreads. It's on by default.
- **`identify_plant`:** the species of the plant in the user's latest photo, by its Latin name, with PlantNet; the model adds the common name. It's on by default.
- **`edit_photo`:** edits the user's latest photo and shows the result in the chat: removes its background, erases something the model names ("the sunglasses"), upscales it or brightens it. Asked for more without a new photo, it edits its own last edit, to upscale a photo it erased something from, say. The model gets only a note that it's done, since it can't see the result. It's on by default.
- **`search_web`:** searches the web with DuckDuckGo, or with your own [SearXNG](https://docs.searxng.org/) server if `SEARXNG_URL` names it (`http://searx.lan:8080`; its JSON format must be on). It gives five results, or recent news stories when the model asks for them. It's on by default; `LITE_ASSISTANT_TOOLS` without it keeps the server offline.
- **`read_web_page`:** reads a page's main text, such as a search result, cut to 4000 characters to fit the context. It reads only public http and https addresses, not this machine or its network, so a page can't steer the model into reading local services. It's on by default.
- **`set_timer`** and **`list_timers`:** timers kept in memory. The server can't speak unprompted, so a finished timer doesn't ring; asking about the timers says it's done.
- **`search_notes`:** searches the user's notes and documents by meaning, with EmbeddingGemma, then puts the closest in order with Qwen3-Reranker. Notes are `.txt`, `.md`, `.pdf` and `.docx` files, and photos of pages, in the user's own notes folder, `users/<name>/notes` in the data directory (see [Where models go](where-files-go.md)), split into paragraphs. Each [user](../guides/manage-users-and-keys.md) searches only their own. Uploading a file to `/v1/files` adds it to them. Notes from before there were users move to the owner's folder when the server starts. See [Documents](../guides/search-your-documents.md).
- **`load_skill`:** instructions the model loads when a task needs them, as the Google AI Edge Gallery's Agent Skills and Claude's skills work. Each skill is a folder with a `SKILL.md`, whose frontmatter gives its `name` and `description`, and whose text is the instructions. Only the names and descriptions go to the model, in the tool's description, so skills cost a line of context each until one is loaded; a skill's instructions can name other files in its folder, which the model can then read too, and no others. The system's skills are in the `skills` folder of the data directory, for everyone, and each user's own in `users/<name>/skills`; a user's skill takes the place of a system skill with the same name. Skills added or changed are seen at the next request, and the tool is offered only to a user who has some. A Claude skill folder works as is, though instructions that run scripts don't, since the model can't run them. With a skill that writes a plant care card in a set format, Gemma 4 E2B loaded it and wrote the card for a snake plant and a cactus, but asked what a peace lily was called. Small models sometimes call a skill by its own name, as if it were a tool; that loads it too.
- **Your own,** from [tool folders](../guides/write-a-tool-file.md), such as the example's weather, Wikipedia, calculator and unit tools, and `ask_for_help`, which asks Claude Code.

`LITE_ASSISTANT_TOOLS` picks which are on by default: comma-separated names, `all` or `none`. A request's `builtin_tools` overrides it with a list of names, or `false` for none: a field of the chat completions and Responses body (`extra_body` in the openai SDK), of the Realtime session or `response.create`, or a comma-separated `/v1/voice` form field. A client's function tool with the same name as a built-in takes its place.

Calls are logged. Responses reports each as an `mcp_call` output item with `server_label` `lite-assistant`, its arguments and its output; the other APIs don't report them.
